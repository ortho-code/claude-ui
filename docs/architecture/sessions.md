# Reading sessions

## Reading sessions

`src/main/sessions.ts` walks `~/.claude/projects/*/*.jsonl`.
Each `.jsonl` is one session transcript with one JSON event per line.
For each file it streams the lines to pull the working directory and the first prompt without loading the whole file, counts the events, and takes last activity from the file mtime.
The renderer groups the results by working directory.

**A session's name is Claude's, or its first prompt**: its custom title, else the title Claude generated, else its first prompt, else `New: <folder>` after the folder it runs in (`sessionLabel`), on every surface.
The app stores no name of its own, and offers none to claude: a fork's name starts as its parent's title from Claude, never its first prompt.
A slash command as the first prompt is named without its slash (`review 35676`), which reads better as a name; the history keeps the slash, since it shows what was sent.
A command Claude runs itself, such as `/clear`, `/model` or `/effort`, is not a prompt, so a session that opens with one is `New:` until something is typed in it.
The app once took such a command for the first prompt and named sessions `/clear` and `/model`, which Claude itself never does: none of the 284 titles it generated on one machine (2026-10-22) starts with `/`.
Claude writes such a command with the command's name first, where a command sent to the model opens with `<command-message>` (claude 2.1.302's templates): 164 commands of the one kind on that machine, each right after a `<local-command-caveat>` record, and 323 of the other, with no third shape.
Claude generates a title from the first prompt that is neither a slash command nor its own plumbing, so a session started with a skill such as `/implement` goes by its command a long while, its title coming late, from a later prompt, or never; and its automatic title generator runs only while the session has no title of any kind, so never once it has a custom title (none of 228 named sessions there got one later).
Rejected: naming a session only by Claude, with `New:` before a prompt and `Untitled:` after, since 63 of the 326 unfinished sessions of one project there had no title, 11 of them real conversations that would then differ only by their dates; and the app sending `/rename`, which makes Claude generate a name, since it would type into a terminal where you may be halfway through a prompt.

**A session's worktree comes from its transcript**: the last of Claude Code's `worktree-state` records, when there is one, says whether the session entered a worktree or left it, and without one the first `cwd` does.
A session the transcript last puts in a worktree carries the worktree's name (`worktree`), and that is where a resume runs.
One that ran in a worktree and has since left it carries the name apart (`leftWorktree`), drawn as the same badge, because it still did its work there, and muted unless its panels follow it into a worktree (below); a resume runs where it is now.
Both are named the same way, so a tree removed since is still named under `<repo>/.claude/worktrees/`, where Claude Code cuts them, and goes unnamed, so unbadged, anywhere else.
The record of leaving does not say why, and two causes write it: claude's `ExitWorktree` tool moving the session out mid-session, and Claude Code moving it back to the main checkout as it closes; both write a `relocated` record just before the exit.
Across this machine's transcripts (2026-10-15), 13 of 14 exits were closes and one a move, and 8 of the closes had messages after them, from a resume later, so what follows an exit cannot tell the two apart.
The tool's call can, and sets `movedOutOfWorktree`: it was seen two records after its exit, in the same turn, and the reader takes it there or before the exit, but not after a later user record, since a call a resume brings is not the exit's, and Claude Code refuses one for a worktree from an earlier session.
The badge is muted either way while the panels do not follow the session into a worktree, since a resume runs where the session is now, and its tooltip says which: worked in the worktree until it closed, or moved out of it.
Claude Code writes `worktree-state: null` again and again after an exit, at each resume too, so only the first one after an entry is an exit.
A Bash `cd` into a worktree changes the `cwd` the records carry and nothing else: Claude Code records no worktree session, and a resume runs where the session started, so it counts as neither.
Counting it was considered and rejected: any record in a worktree would badge a one-off look inside one, and a share of the records would be a threshold nothing can check.
The panels do follow a session into a worktree it reached that way, by what it changes there, and its badge lists that worktree (below).

**Where a session works is the checkout it last changed a file in** (`workCwd`), which is where a panel without a folder of its own looks ([§ Where a panel runs](panels.md#where-a-panel-runs-the-cwd-option)), while the session itself still runs, resumes and is badged where `cwd` says.
It is the checkout, the main one or a linked worktree of the session's repo, holding the newest file claude changed with Edit, Write, MultiEdit or NotebookEdit, read from claude's own records only, since a transcript's `api-request-blob` records replay earlier calls.
A file git ignores, and one outside the repo's checkouts, such as one behind a link out of it, is passed over for the change before it, so notes and local settings do not pull the panels back to the main checkout.
A `worktree-state` move after that change wins, since it puts the session where `cwd` already says.
A change in a worktree it can tell is gone, a listed one whose folder was removed or a `<repo>/.claude/worktrees/<name>` folder git no longer lists, leaves the panels where the session runs, and not in the checkout of an older change, which would be a guess; so does the chosen checkout's folder going, which a listing asks afresh as it does for `cwdExists`.
A worktree elsewhere that git has pruned cannot be told from a folder outside the repo, so its changes are passed over as those are.
The checkout is chosen when the transcript is read, and git's answers and real paths are kept for the run, so a worktree pruned or a `.gitignore` changed since counts from the transcript's next change, or the next launch.
The records' `cwd` was weighed first, and it does not say where a session works: one session here left its worktree by `ExitWorktree` and made 75 changes in it by path over six days while every record said the main checkout, and its records later moved back to the main checkout with remote work, with a `cd` into a temporary folder, which claude's shell answers by returning to the folder it started in, and after a pause, none of them with a change there.
Over this machine's transcripts that touch a worktree (112 sessions, 2026-10-26), asked at each of the 2,760 prompts followed by a change where that next change went, the last change was right at 94% of them; the records' latest `cwd` at 91%, moving the panels 268 times against 78; the latest worktree the records reached at 92%, which never comes back to the main checkout; and the reading before this, the worktree records alone, at 87%.
The measure takes the next change as the right answer, which favours this rule by construction; the six days above do not depend on it.
What it cannot see is a change made through a shell command, such as `sed -i` or `git mv`; a subagent's changes are left out, and none of this machine's subagents made one in a worktree.
The cost is the parse of the lines that call a file tool, looked for in claude's own records only; `git worktree list` once per repo and listing, for a repo with a transcript re-read that changed a file; and `git check-ignore` only for a session that changed files in a checkout other than its own, or that left a worktree, one call per checkout each time it is re-read, its answers kept per file for the run, without `--no-index`, so a tracked file that matches a pattern still counts as git shows its change.

**A session's worktree badge lists the checkouts it worked in** (`checkouts`): each checkout of its repo it changed a file in, counted as the work folder counts a change, newest first, beside the worktree the badge names, where the session runs or that it left; nothing when it would hold only that worktree, or for a session without a badge only the checkout it runs in, so a list always says something the badge does not.
The badge then carries their count and opens the list, which the session's menu holds too, and a session that changed files in a worktree it never entered, by path or after a `cd`, wears the badge for it; the worktree filter counts it, since the badge, the tab's mark and the filter are one rule (`worktreeMarkState`).
It is in the accent while the session runs in a worktree or works in one, and muted otherwise, so a session whose panels follow it into a worktree ([§ Where a panel runs](panels.md#where-a-panel-runs-the-cwd-option)) wears it as a worktree session; one in a worktree whose panels follow it into the main checkout keeps the accent while their header names the main checkout.
Only a change counts, as for the work folder: the worktrees on the records' `cwd` were weighed and left, since of the 17 sessions on this machine (2026-10-26) whose records reach a worktree the badge does not name, 9 changed nothing there with claude's file tools, where the changes name 12: 8 of those 17, and 4 that ran in or left a worktree and changed files in the main checkout, 2 of them in another worktree by path as well, which the records' worktrees leave out.
A session that left a worktree is asked about every change, since the checkout it runs in now is one besides the worktree its badge names, listed when git shows its change there.
Whether a checkout is gone is the reading's, or its folder missing at the listing, which stats it with the other folders; the reading's answer stays until the transcript changes, as the work folder's choice does.

**A session's PRs come from its transcript too**: Claude Code writes a `pr-link` record naming a PR's repository, number and page, and writes the same one again and again through a session, so each is kept once, in the order first linked (`prs`), and drawn as a mark on the row that lists them.
A record says the PR is linked to the session, not who opened it, so the mark says "linked": over one machine's transcripts (2026-10-14), 96 of the 98 PRs linked were the user's own, and the other two a colleague's that a session worked on.
A fork's transcript copies none of its parent's records, but in four of the five families there with a PR, the fork's opening records link its parent's PR afresh, so a fork tends to show its parent's PR from the start.
Claude Code links no PR for a review posted on it, nor for a comment posted through `gh api`, so the reader also links the PR of each one claude posts (`src/main/postedprs.ts`): `gh pr review|comment` naming the repository with `--repo` or the PR by its URL, and a `gh api` POST, given as the method or implied by a body, to `repos/<owner>/<repo>/pulls/<number>/reviews` or `…/comments`.
Each invocation in a command is judged on its own, split at the shell's separators outside quotes, subshells and substitutions included, with heredoc bodies left out, so a `-f` in one invocation never makes a read in another a post, and `gh` counts only as the command an invocation runs.
A substitution inside double quotes stays part of its word, so a `gh` command run there, or a heredoc it opens, is not read.
A PR named by a bare number names no repository, and is left out rather than guessed from the folder's remotes, which `gh` chooses among by rules of its own; over 30 days' transcripts here (2026-11-07), 88 of 89 posts named it.
GraphQL review mutations name a PR by node id, so they link nothing.
A PR is kept once whatever its repository's capitals, the spelling first seen kept, since Claude Code's records and the commands claude runs spell one repository both ways.
The same holds across sessions: everything that tells PRs apart goes by the reference in lower case (`prKey`, `src/shared/prs.ts`), as GitHub reads it, so a PR two sessions spell differently is asked once, seen once (`prSeen`, read under that key, an entry an earlier build kept under each spelling read once), and its change marks both; only what is shown keeps each session's spelling.
A panel row's `session` action may name its PR, and a new session started from it is linked to that PR: no transcript names it until the session acts on it, so the app keeps the link in `meta.json` (`prLinks`, by session id), gone when the session is deleted in the app, and the listing puts those links before the transcript's, each PR still once (`withPrLinks`, `src/shared/prs.ts`).
A link is kept by its page and read back from it, so only an address shaped like a GitHub pull request page is kept.
Until the listing names the new session, which is once its first message is in its transcript, its row shows no PR and nothing is asked or marked for it; a PR seen for the first time marks nothing, as any PR does, so only its later changes do.
The link stays with that session's id: neither a fork nor a `/clear` successor carries it, as neither carries a note.
What a PR's state is, open or merged, is not in the record, so it is asked of GitHub.

**What GitHub says of a PR is asked with `gh`**: main runs `gh api graphql` through the login shell (`src/main/prstatus.ts`), on the person's own `gh` login, so the app keeps no token, and `gh`'s stderr comes on fd 3, apart from the shell's job-control lines.
It asks in two steps, because asking more than a PR's state is slow (measured 2026-10-21, 103 PRs in one repository: 25 PRs with every field took 3.4–4.1 s, the state alone of all 103 under one): a PR not known yet, or closed, is asked its state, and one known to be open every field.
Both asks also ask what your role is told from, whether you wrote it, your latest review and a request for your review, so a merged PR has a role too; the open-PR ask adds its head and each reviewer's latest review (`latestOpinionatedReviews`, asked for reviewers with write access, which on the PRs linked on 2026-11-06 held only approvals and requests for changes), which give the approvals and whether new commits came since your review.
Measured 2026-11-06 on the PRs linked then: the open-PR ask was no slower at 25 PRs with these fields, and 100 PRs asked their state, whether you wrote them, and your latest review's id and state answered in 1.5–1.7 s, three times of three.
A pending review of yours counts as none, since it is not submitted; whether GitHub gives one as your latest review is not known, as no linked PR had one.
A merged PR is not asked again while the app runs, and the statuses are kept in main's memory only, so a launch asks again; a file across restarts was weighed and left, a file and a writer more for under a second saved.
A request with no answer — no `gh`, no login, offline, or still going after 30 seconds, when its process group is stopped as a panel's run is — leaves every mark in the accent with its tooltip saying why, since a status that may be stale should colour nothing.

**The window asks through the gate a panel's runs go through** (`RunGate`, `panels/types/sessions/pr-status.ts`): when the PRs the listing links change, then at the delay the answer calls for, a minute while any open PR's checks run, five while any PR could still change or the last ask got no answer, and never once every one is merged and the last ask was answered; the window coming back into focus asks at once, once the last answer is a minute old.
Only while the `prStatus` setting allows it: off, or before the settings are read, an ask asks nothing, so a launch with it off never runs `gh`.

**A PR changing in a way that needs you marks every session that links it** (`prChanges`, `settleChanges`, decided 2026-10-29), as needing you with its changes as its reason ([§ Tab lifecycle](terminal.md#tab-lifecycle-a-tab-can-exist-without-a-process), [§ Status cues](status-cues.md#status-cues)): something that needs you is there now and was not seen before — checks failing, a merge conflict, changes requested, an approved review, merged or closed — every one of them where several come in one answer, strongest first, so an approval that comes with failing checks is not lost once they pass; and a closed PR open again, as `reopened`, with everything it holds then, since a closed PR held none of it.
Each is told apart (`conditionsOf`) rather than from the PR's words, which name only the strongest: from the words, changes requested under failing checks read as new once the checks passed, a conflict under failing checks never showed, and an approval while checks ran never read approved (found by the claim check, 2026-10-29).
So an approved PR whose checks run again after a push and pass marks nothing, and being a draft, checks running or a review required never mark by themselves, being noise for a session parked to wait; a draft whose checks fail marks as any PR does.
A conflict GitHub has not worked out yet, as after a push, counts as what was known of it (`withKnownConflict`), so a conflict that stays does not mark again each time it comes back.
A second request for changes while one already stands, another reviewer's or a new round of the same one's, marks again (`asksForChangesAnew`, decided 2026-11-06): GitHub's review decision stays changes requested throughout, so it is told from the ids of each reviewer's latest review asking for changes, kept with the PR's status for this alone, a new id being a new request.
Every session not finished is marked, running or not, since claude working or asking shows over the mark anyway and your next prompt there settles it; a finished one is done.
**A change marks only where its type fires for your role on the PR** (`roles` in the type's file, `firesFor`, `marksFor`, decided 2026-11-06): failing checks, a conflict, changes requested and approved ask the author to act, so as shipped they fire on your own PRs alone, where a review session was marked for a colleague's red checks before; new commits since your review and your review asked fire for a PR you review; reopened, merged and closed fire for every role.
New commits since your review is the PR's head no longer being the commit your latest submitted review was on, kept as true or false rather than as commit ids, so it marks once per review: a second push before you review again finds it true already, which one mark per round asks of you anyway (decided 2026-11-06); a rebase moves the head too, so no type of its own tells one apart, which would need each PR's timeline asked.
A field of your review that the status seen before did not know, as one kept before the app asked it, counts as what is seen now (`withFieldsKnown`), so it coming to be known marks nothing.
The role is the one GitHub gives with the change, and a status without one, kept before roles were asked, fires no type that lists roles, so nothing is marked on a guess; a type that lists no roles fires for every role.
The roles are the type file's, changed by id like any field, so a reviewer who wants a PR they review to say it is ready to merge adds `"reviewing"` to `pr.approved`; a setting of their own was turned down as a second place for what the file says, and the field becomes the type's query once types are queries.
GitHub keeps the review decision at changes requested while any reviewer's latest review requests changes (seen on the PRs linked 2026-10-29: one stayed so beside another's approval, and nineteen turned approved only once their requester approved or was dismissed), so approved marks once no request is left, without the app working that out.
**What GitHub was last seen to say of each PR is kept in `meta.json`** (`prSeen`, each PR's status), since main keeps the statuses in memory only and a PR merged overnight has to have something to change from; each answer is compared with it and then replaces it, and the window reads main's copy once; a read that fails marks nothing that time and is tried again at the next ask, which goes on as before.
A PR seen for the first time is recorded and marks nothing, whatever it holds, so a PR made and merged while the app was closed or the setting off marks nothing; one with no status keeps what was seen, and an answer in which any request to GitHub failed changes nothing, what it did learn waiting for the next whole answer.
A PR no session links any more stays in it, and is compared with what was seen of it if it is linked again.
The first run, with nothing ever kept and the setting on, comes with the first answer in which no request to GitHub failed and that has a status for any PR, which may be a later launch's where GitHub could not be reached, and marks only the sessions with a tab or a later mark whose PRs already need you by that answer, the ones set aside to wait; a PR that answer had no status for is seen for the first time later, and so marks nothing then: on the PRs linked 2026-10-29, 78 sessions had every PR merged or closed, 72 of them with neither, most untouched for over a month, which is the pile of sessions done with but never marked finished, and not news.
Turning the setting off empties what was seen, read or not, and so does a launch with it off, so turning it on starts from the PRs as they are then and marks only what changes after (decided 2026-10-29), the first run included for a setting that was off from the start; comparing with what was seen before it went off was weighed and left, as harder to predict.
Rejected: marking only the sessions whose claude is not running, since a PR merging under a running session would say nothing until it stopped; and marking every session already needing you at the first run, for the pile above.

**A PR's colour comes from the tone words a list panel's rows use** (`src/renderer/prstatus.ts`, `tone.css`), never a palette of its own: red (`danger`) for failing checks or a merge conflict, yellow (`attention`) for changes requested, green (`positive`) when approved, not a draft, with its checks passed or none and GitHub having worked out that it does not conflict, the accent (`normal`) for any other open PR — waiting on a review or its checks, a draft, or not yet known to conflict or not — and for one with no status, and grey (`muted`) once merged or closed.
Yellow and green mean what they mean on a session's dot beside it on the row, something asking you and done with your move next; red is what a failed panel run's dot shows, something gone wrong.
A session's mark takes whatever most needs a person among its PRs, so it is grey only once every one is merged or closed; its tooltip counts the PRs that set its colour by state, and its list and the session's options lead each PR with a dot in its colour and name its state on a line under it, with your role where the PR is not yours and an open PR's approvals, since the reference and the words together outrun a menu's 300px, or, for a PR with no status, a hollow dot and no words.
Muted is the grey a muted worktree mark has, not the list rows' dimming, since the mark stays a control and a dimmed control reads as disabled.
Approved is GitHub's review decision and, where `approvals` in the settings names the PR's repository, that many approvals counted from the reviews (`isApproved`): the number only raises GitHub's bar, since GitHub enforces its own and a PR it does not call approved would not merge (decided 2026-11-06); a team that merges on two where GitHub asks one sets two, and below it the PR reads as review required, the accent, its count in a session's options.
The repository's own number is not asked of GitHub: its branch protection answered a login without admin rights 404 (asked 2026-11-06), and the team's number may be a habit GitHub does not hold, as one approval enforced and two agreed was.
An open PR with no review decision stays the accent even with its checks passed, since GitHub's schema describes the decision only as "the current status of this pull request with respect to code review", and says nothing of what a missing one means.
GitHub's own colours were weighed and left: they are a second palette, and their green for "open" says the opposite of the dot's green for "done" on the same row.

## App-side metadata and session groups

Everything the app knows that Claude Code doesn't — pins, finished sessions, open tabs, per-project display names, custom groups, the window's geometry, the sidebar's view state and where the layout was left — lives in a `meta.json` under the app's own user-data directory.

The finished sessions are kept in `meta.json` under `finished`, by session id with when each was finished.
A file an older build wrote holds them as `archived`, which is read into `finished` and dropped at the next write, and `ui.filters.archived` the same way into `ui.filters.finished` (decided 2026-11-05).
A build from before then reads none of them from a file this one wrote, so going back a build means restoring `meta.json.<version>.bak`, the copy the first write of a new version keeps of the file as the outgoing build left it (`main/backup.ts`).
An older build keeps the `finished` it does not know and writes its own `archived` beside it, and the newer build then reads `finished` first, so what was finished in the older build is lost on coming back unless the copy was restored; two builds of the same version take no such copy.

The app's own preferences are not there: they are what you chose rather than where you left off, neither should be able to reset the other, and they are yours to edit and share, so they live in the config folder (see The config folder).
They were kept in `meta.json` as `settings` until then; `moved` records each thing that has moved out, so the move is made once, and the old copy stays where it was for an older build to find.
The session store is never written to: `~/.claude` is read-only as far as this app is concerned.

A project is listed while it has a session that is not being deleted, finished ones included.
One whose sessions are all finished stays in the session list and the switcher, counted at none, with a line under its heading saying so and its groups and its `+` with it, so work can start there again; one rule finds such projects for both, and for the fall back to All (`finishedOnlyProjects`).
Deleting its sessions is what takes it away, and the project on show then falls back to All.
A filter leaves it out, as it leaves out any project with no match, and the finished view lists it with its sessions.
Keeping every project the app has ever known, with sessions on disk or not, was weighed and left for later: it needs a look at whether each folder is still there, and a way to remove a project, or the list would only ever grow.

A project gets its place in the project order, in front, at the next full read of the sessions (at launch, or after a session is deleted), and keeps it, since no write takes a place away (`seedProjectOrder`).
So the order holds projects the unfiltered list does not show, those whose sessions are being deleted or deleted, and roots a session no longer resolves to, and a move from a project's options steps over them: it passes the next project on screen and leaves the rest in their slots (`movedProject`).
Moving one slot at a time, a project put in front of such a root swapped with it on its first move down, and looked like nothing happened.
A project that turns up while the app runs is drawn last, with no place until the next full read, so until then it offers no move, and the project above it no move down.

Writes are serialized through one queue and land via a temp file renamed over the target, with the previous good copy kept as a backup, so a crash mid-write can't leave the file half-written.
Reads are tolerant by design: unknown or malformed entries are dropped rather than trusted, and older field names are still understood, so an older `meta.json` upgrades in place without a migration step.
