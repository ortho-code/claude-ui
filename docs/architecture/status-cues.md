# Status cues

## Status cues

Rather than parse terminal output to guess a session's state, the app drives status from Claude Code hooks, and reads the transcript only for the ends no hook reports (below).
On startup it writes a hook script and its own settings file to `~/.config/claude-ui/`, and passes that file to `claude --settings`, whose hooks merge with the user's own — so claude-ui never writes into `~/.claude/settings.json` (an earlier version did, and still strips those entries when it finds them).

**Ready is claude stopped at its prompt with nothing running** ([decided 2026-11-08](../decisions/0195-ready-names-claude-stopped-at-its-prompt.md)): the status, its label, the needs-you type `claude.ready` and its colour all use the one word.
A status file left by 0.3 or earlier says `idle`, and is read as `ready`.

Seven events map straight to a status: `UserPromptSubmit` → busy, `PostToolUse` → busy, `PreCompact` → busy (compaction, below), `Stop` → ready (or background, below), `Notification` → waiting (but for claude's idle notice, below), `PermissionRequest` → waiting, `SessionEnd` → closed.

**Claude's idle notice is ready, not waiting.**
A minute at its prompt without input (claude's default, which its own config can change), claude sends `Notification` with `notification_type: "idle_prompt"` ("Claude is waiting for your input"), at most once per turn (measured on claude 2.1.289).
It says the turn is done, which the `Stop` before it already said, and asks nothing, so it is not waiting ([decided 2026-10-28](../decisions/0124-claudes-idle-notice-is-ready-not-waiting.md)).
The script writes nothing for it over ready, background or waiting, so a read mark and the work a `Stop` listed stay, and a question still open keeps saying so; over any other status, such as a busy no hook ended, or with no status file, it writes ready, since claude is at its prompt.
**Notices of something finished are not waiting either.**
Claude 2.1.310's binary sends `auth_success` for "Claude Code login successful", `agent_completed` for an agent that finished or failed, and `computer_use_exit` for "Claude is done using your computer", none of which asks anything, so the script writes nothing for them ([decided 2026-10-28](../decisions/0128-notices-of-something-finished-are-not-waiting.md)); whether they reach the hook at all is unmeasured, and if they do not, nothing is lost.
Claude 2.1.316's binary also sends `elicitation_complete` when an MCP server confirms a form it asked you to fill in is complete, and `elicitation_response` once that form has its answer, so a session whose MCP server asked through a form could go waiting after it was answered; the script writes nothing for them either ([decided 2026-11-08](../decisions/0190-an-answered-mcp-form-is-not-waiting.md)), and neither has been seen live, which needs an MCP server that asks through a form.
Every other notification still writes waiting: a permission prompt, a question, a background agent waiting on you (`agent_needs_input`, `worker_permission_prompt`, "… needs permission for …"), a message claude chose to send you (`push_notification`), a login that needs attention (`auth_storage_failure`), and any kind a later claude adds, since missing a question is worse than a waiting too many.
The other kinds the binary names (the form's own `elicitation_dialog` and `elicitation_url_dialog`, `quota_auto_resume_*`, `model_refusal_fallback`, `computer_use_enter`) are not set as a literal `notificationType` in 2.1.316, so when they are sent was not read, and they write waiting.
`plugin_notification`, a notice a mod sends, is set as a literal and writes waiting too, since it may or may not ask something.
The last `Stop`'s payload, which the app reads for what still runs and what is scheduled, stays as that `Stop` left it.

**A permission prompt is waiting from the moment claude asks.**
Claude sends a prompt's `Notification` about six seconds after the prompt appears, and none at all once it is answered sooner, so for a prompt within a turn the dot used to say busy for those six seconds, and throughout a prompt answered quickly.
By claude's source the six seconds count from the later of the prompt appearing and the last key pressed at it.
That notice is the same question again, so the script writes nothing for it over the waiting a `PermissionRequest` wrote, which keeps a dot marked read meanwhile marked read.
`PermissionRequest` fires as the prompt appears, and fired for no call claude let through without asking (measured on claude 2.1.289: four prompts, and seventeen calls in default mode and three in auto mode that needed none), so it does not flash the dot to waiting on an ordinary tool call; another `PermissionRequest` hook that answers the request itself would, until the tool has run, or, if that hook turns it down, until the next hook (by claude's source).
Approving the prompt is the tool running, `PostToolUse` → busy, and turning it down without a word, with Esc or from its menu, is an interrupt in the transcript (below), which ends the turn (both measured).
Turning it down with feedback, which a Bash prompt takes as its No amended with Tab (a WebFetch prompt has no such field), does not interrupt the turn: claude writes the refusal with the feedback and carries on, and no hook fires, so the dot said waiting until its next tool had run or the turn ended (measured: 1.0 s when claude answered at once, 7.9 s when it thought first); the transcript now ends that waiting with busy (below).
Esc at a background subagent's prompt refuses its call without an interrupt; in the one run, the subagent then finished on its own, and its end started a turn of the session's two seconds after the Esc.

**A turn that ends with work still running has not finished, so it reads as `background`.**
`Stop` carries the work the turn started that still runs, such as a backgrounded shell, a monitor or a subagent sent off in the background, as `background_tasks`, and while that list holds anything the script writes `background` instead of `ready`.
For a backgrounded shell, a monitor and a background subagent, the work's end made claude start a turn of its own, which ended in a `Stop` with the list up to date, so nothing else needs hooking (measured on claude 2.1.289, one probe each).
It takes ready's place and no other's: busy already promises more output and waiting must always win, so it can never hide a session that needs you, which is why it is a state and not a mark of its own beside the dot.
To the roll-ups it is busy, with no "ready" to carry and nothing to mark read, while stopping it sends the two presses a ready session gets, since claude's prompt is open.
With a background shell running, claude answered those presses with a question, exit and stop the work or stay, rather than leaving (measured once; claude's own code leaves some kinds of work out of that question, and a worktree session asks about its worktree instead), and the tab stays up for it as for any question on the way out.
Work you stop yourself, from claude's own task list, started no turn and fired no hook at all (measured with a background shell and a monitor; a subagent stopped that way started a turn, whose `Stop` ended it as above), so the transcript ends it (below).
The dot's tooltip names the work by the type claude gives each piece (`shell`, `subagent`, …), counted per type, as in "2 shells, 1 subagent"; a monitor that watches a shell command arrives as a `shell`.
The script reads those from the `type` keys, which in `Stop` only the list's entries have, and a claude too old to send the list reads ready, as before.
The launch read passes on the status alone, so a `background` read back at launch says no more than that.
Scheduled wakeups (`session_crons`, from `/loop` and the like) are not counted: nothing runs until they fire, and counting them would keep a looping session from ever showing finished; they show as a clock of their own instead (below).
An artifact claude watches for comments is not counted either.
Publishing one arms a watch wherever claude allows one (by its source, not in a remote session, for one), and `Stop` lists the watch as a `monitor` while it lasts: one armed by a publish was still listed about 50 minutes later (measured on claude 2.1.296), and the session read background from then on while nothing ran.
By claude's source, the watch on the artifact published last is never retired for being idle, and a comment sent to Claude while its auto-replies are armed summons a turn of its own, as a scheduled wakeup starts one.
A monitor of your own on a websocket is listed as `monitor` too (by claude's source), so the script tells a watch by its description, which claude starts with `live updates for artifact` every time, and takes one monitor off the list for each watch; worded otherwise by a later claude, a watch would count as work again.
An end the transcript reports (below) hands the script each piece of work's description as well, so a watch the last `Stop` listed is left out there too.
Claude's idle notice (above) does not end it either: claude sends it while a shell it started still runs, and the script writes nothing for it over `background` (measured on claude 2.1.289, with a background shell).
Every other notification, such as a permission prompt or a question, still writes waiting over it.
Its dot is busy's spinning ring around a small core of ready's green: the turn is done, and work goes on.

**A session marked as needing you shows it where claude says nothing more pressing** ([§ Tab lifecycle](claude.md#tab-lifecycle-a-tab-can-exist-without-a-process) for when it is marked and what settles it).
**Which state a dot shows is one list, the strength order** (`strength` in `settings.json`, `shared/status/looks.ts`; [decided 2026-11-06](../decisions/0173-a-dots-state-is-picked-by-one-strength-order.md)): every status and the needs-you categories, the dot showing the first that holds, a reason by its category's place.
`needs-you` in the list stands for every category it does not name, in Now's order, so a category added later has a place in a list written before it; a category may be named on its own anywhere, such as Back to work over busy.
Your turn has no place of its own, its two types being the statuses `waiting` and `ready` themselves.
The default, `["waiting", "busy", "background", "needs-you", "ready", "closed"]`, shows busy, background and waiting over the mark, and the mark over ready, `closed` and no status ([decided 2026-10-28](../decisions/0120-a-needs-you-mark-shows-over-ready-not-over-work.md)).
A list with a mistake is not used at all, the default in force and the mistake named in Settings' Appearance section, which has no field for it yet; its categories are checked against the needs-you categories in force, the bundled ones with `needsYou` applied, in main's read of the settings (`settingsView`).
One rule applies it for a session's dot (`shownState`, through `dotStatus`) and every roll-up alike (`sessionNudge`, the switcher, a group's jump menu, the tab bar's chevron, the rail icons), and what the dot shows of a reason names its type (`needs:<type>`), the strongest category's newest.
**A roll-up puts what asks for you before what works**, each in the order (`strongestNudge`, [decided 2026-11-06](../decisions/0177-a-roll-up-puts-what-asks-for-you-before-what-works.md)): busy over a mark on a dot still leaves a marked session over a busy one in the switcher; with the default that is waiting, each category, ready, then busy.
**The switcher counts what asks for you elsewhere** (`elsewhere`, `projectsForSwitcher`; [decided 2026-11-08](../decisions/0202-the-switcher-counts-what-asks-for-you-elsewhere.md)): its title shows how many sessions in projects other than the one on show ask for you, a session counting when its part in a roll-up asks for you, so the count always agrees with the dots you find when you go there; in All it counts every project.
The count is drawn in the colour of the strongest of what it counts, in the count pill the headings wear; with nothing asking and something at work elsewhere, it is the busy dot without a number, its tooltip saying how many work; each project in the popover shows the same for its own sessions, the one on show too.
The sessions panel's rail icon keeps the roll-up over every project, the one on show included: folded, the sidebar shows no project, so its icon answers whether anything anywhere wants you.
Its dot is mauve by default, pulsing at waiting's pace; mauve rather than waiting's yellow, since claude is not the one asking, and rather than peach, which at 9 px read too near yellow (chosen from a mock of six).
**How each state is drawn is its look** (`looks` in `settings.json`, `shared/status/looks.ts`; [decided 2026-11-06](../decisions/0180-how-each-state-is-drawn-is-its-look-in-settings.md)): for a status, `needs-you`, a category or a type, by its id, a `colour` from Catppuccin Mocha's names or `#rrggbb`, a `mark` (`dot`, `ring`, `spinner`, or an icon of the rail's set), a `core` inside a spinner, a `pulse`, and `looksLike`, another id to take the rest from.
A look resolves field by field (`resolvedLooks`): its own field, and every field it leaves out from the one it looks like, as that one resolves, or where it looks like none, from its category's for a type, `needs-you`'s for a category, or the default for a status and `needs-you`, which are the dots as they were; so nothing changes until something is set, and a type left alone follows its category.
A reason of a type the needs-you files do not define, which ranks at `needs-you`, draws in the needs-you look (`looksStylesheet`).
Looking like another copies the look and never the place in the strength order.
Your turn's types have no look of their own, being drawn as `waiting` and `ready`.
Looks with a mistake are not used at all, the defaults in force and the mistake named in Settings' Appearance section beside the order's; their ids are checked against the needs-you categories and types in force as the order's categories are.
Two looks alike is allowed and does nothing more: the order still decides what a dot shows, and its tooltip names it; the defaults share one look between every category, so a warning at each clash would fire on them.
Read and muted are not looks: they dim and still any look, as they always did.
Every dot that stands for a session or rolls sessions up draws its look, and an attention toast's edge its colour; a panel's run, a PR's tone, but for a PR yours to review again, which takes its type's look's colour ([Reading sessions](sessions.md#reading-sessions)), a stopping tab's square and waiting's and ready's colours used elsewhere, such as the "hasn't left" words, keep their own.
**Its tooltip and its menu's header list every state the session is in**, a line each, in the strength order, the dot's first, behind what its tab says (`stateLines`, [decided 2026-11-06](../decisions/0174-a-dots-tooltip-lists-every-state-the-session-is-in.md)): a session busy and marked says "Busy" and then why it is marked, so a mark its dot does not show is still there on hover.
A session with several reasons has one dot for them all, each reason on a line of its own where its category ranks, and within one newest first (`needsYouLines`).
A PR's reason names it by number and title, the title cut at 60 characters, "Needs you — PR #35777 · Scheduler tick per host — merged", by number alone while no title is known, "Needs you — PR #35777 merged", and by its repository too, "PR acme/app#35777", only where the reasons name PRs in more than one; the PR badge beside the dot already says the rest.
Changes found in one answer, a reason of its own type each at the same moment, are named together on one line in the same order, "PR #7 checks failed, approved", and the line ranks by its first; the PR's next change replaces them.
A rail icon shows it in its colour where no session waits, with the default order; an order naming a category before `waiting` shows that category's mark over a waiting session there too.
The rail icon's corner draws any look as a plain dot of its colour, never its icon or ring, since an icon on an icon's corner would read as neither; the one place a look is drawn otherwise, on purpose.
A click on it marks it read, dimmed and still, as for ready and waiting; the mark stays, since seeing it is not settling it.
A new reason takes the read mark off, one that replaces an older reason of its kind too, such as a PR's next change, as a new status from claude does (`markNeedsYou`), and so does a set-aside day coming, whether it brings the reminder or lights up the reasons the mark muted (`settleDueSetAside`), so news is never born read ([decided 2026-11-11](../decisions/0214-a-new-needs-you-reason-is-unread.md)); putting reasons back, as Undo does, leaves the read mark as it is.

**Every reason a session needs you for is of a type, and every type belongs to a category**, a section of the Now view to come: Your turn, Back to work, Ready to merge, Look again, Reminders and Finish up, in that order ([decided 2026-11-06](../decisions/0185-needs-you-types-and-categories-ship-as-files.md)).
The app ships them as files, one JSONC object each, in `bundled/needs-you/` beside `assets/`, written as a person's own file would be, so each can be changed or switched off by its id like anything else the app ships.
A category says its `kind`, `id`, `label` and `order`; a type its `kind`, `id`, `label` and `category`; either may say `"enabled": false`; any other field is a mistake, so a misspelt one is named rather than ignored.
Main reads them once as it starts (`readBundledNeedsYou`, checked by `needsYouRegistry`) and hands them to the window (`getNeedsYouTypes`), which names each reason's category in the sessions file a panel type is given; it reads them with Node's fs, which lists and reads inside the packaged app's asar (measured on Electron 43.2.0); a file with a mistake is logged and left out whole, and two files with one id are both left out, but a mistake there is the app's own bug, which a unit test catches before a build.
Claude asking and claude ready are types too, Your turn's, read from claude's status rather than stored, since they come many times an hour and the transcript already holds every turn.
**`needsYou` in `settings.json` changes one by its id, field by field, or switches it off with `"enabled": false`** (`withChanges`, on `overriddenById` in `src/shared/config/overrides.ts`; override by id [decided 2026-11-04](../decisions/0162-shipped-parts-are-overridden-by-id-field-by-field.md), kept in `settings.json` [decided 2026-11-08](../decisions/0191-needs-you-changes-live-in-settings-json.md)), the one rule every kind the app ships this way is to take, views and a plugin's parts later: a field an entry names replaces the shipped one's, and every other stays the shipped one's, so a later version's change to a field left alone still arrives.
A category may change its `label`, `order` and `enabled`, a type its `label`, its `category`, naming one there is, and `enabled`, and a PR's type its `roles`; `needsYou` is used whole or not at all, as `looks` and `strength` are: one entry that names an id the app does not ship, changes `kind`, holds no object or gives a field a value that cannot be used leaves every category and type as the app ships it, and Settings names the mistake in its Needs you section.
What you add of your own, such as a type, is to go in a folder of its own.
Main applies them in its read of the settings (`settingsView`), which also checks the strength order and the looks against the result, and gives the window the result (`getNeedsYouTypes`, and `needsYou:changed` when a change to the file changes it), which it holds (`needsYouTypes`).
A type is on while it and its category are (`typeIsOn`); one that is off marks nothing from then on, so the launch, a set-aside moment coming and a PR's change each ask before they mark, and the marks it already made are settled `off` into their sessions' histories, at launch and at the change alike (`settleSwitchedOff`), so switching it off retires them rather than hiding them, and switching it on again marks only what comes after.
A PR's colour stays, since that is `prStatus`'s asking, and so does a set-aside moment taking its bookmark off; a type the window has not heard of yet is on, so nothing is switched off on a guess.
Your turn's types switched off change nothing yet: claude asking and claude ready show on the dot as statuses, and the types are for the Now view; Undo of a close can put back a reason of a type switched off since, which is then settled `off` again at once.
Settings lists them under Needs you as they stand, each category in Now's order with its types, each in its look, saying which are off, which PRs a PR's type fires for and what `needsYou` changed, Your turn's drawn as the statuses they are; it has no switch for them yet, and names where they are set ([decided 2026-11-08](../decisions/0198-settings-shows-needs-you-without-an-editing-screen.md)).
Its Appearance section lists the strength order in force the same way, top to bottom, `needs-you` opened into the categories it stands for (`expandedStrength`); a type's look shows on its row under Needs you rather than a second time there.

**A session set aside carries a mark of its own, beside the dot rather than on it** (`setAside`, [decided 2026-10-29](../decisions/0140-a-set-aside-session-has-a-mark-of-its-own.md)).
It is kept in `meta.json` by session id, with the moment it comes back or none for whenever, and when it was set (`SetAside`), so it outlives the tab, whose close, stop or start leaves it; its pure rules are beside the needs-you mark's (`session-marks.ts`), so the window keeps its copy by main's.
It was called Later until 2026-11-05, and `meta.json` kept it as `later`, which a read still takes in until the next write drops it, as `ui.filters.later` is read as the set-aside pill; nothing of Later was released, so only a build from source has written either.
**Set aside… in the session's menu opens one dialog** (`set-aside-dialog.ts`, [decided 2026-11-05](../decisions/0171-set-aside-opens-one-dialog-that-only-marks.md)), for a session with a tab or without, running or not.
**What it does to a claude running in a tab of the session is `setAsideRunning`** ([decided 2026-11-11](../decisions/0212-setting-a-running-session-aside-stops-it.md); `setAsideTabs`, `claude/closing.ts`): `"stop-close"` by default asks claude to leave, as Stop asks, and closes the tab once it has gone, `"stop"` keeps the tab cold, and `"keep"` leaves it running; a tab with no running claude, starting or already leaving is left as it is.
Every set aside raises a toast saying until when, "Set "<title>" aside until Fri 6 Nov, 09:00", from the menu too, with Undo as its only button: at once, and again as each claude goes, its Undo then covering every tab closed or stopped so far.
The Undo takes the marks off, puts the tabs it closed back where they stood and starts claude again where it ran, as `undoRunning` says ([§ Tab lifecycle](claude.md#tab-lifecycle-a-tab-can-exist-without-a-process)); in a tab whose claude is still leaving, the tab stays and claude starts again once it has gone.
A claude's exit counts as the set aside's only while it is still leaving for it and the session is still set aside: a leave called off, by a prompt, a `/resume` or a `/clear`, takes the tab off the set aside, and a Close tab or Finished pressed meanwhile takes the exit over, with its own toast.
The dialog asks two things in one act: when to come back, from the choices in the settings (`setAside`, by default Tomorrow, In 1 week and Whenever) and Pick a date…, a day no earlier than tomorrow, since a time later today is what a choice such as `in 2h` is for, from the calendar the filter uses with a time under it, opened inside the dialog; and where it stands, a field holding the session's note, focused with the caret at its end.
The choices are buttons wearing the date presets' pill (`pill.css`), since both pick a moment, the one chosen filled as a preset that is on; nothing is chosen as the dialog opens, also for a session already set aside, whose line under the title says until when, so Set aside always means a choice made there, and it is unavailable until one is, or with Pick a date…, until a day and a time that reads.
Ctrl+Enter sets aside, as it saves a note; Esc and Cancel change nothing.
**Where it stands is the session's note**, not a line of the mark's own ([decided 2026-11-05](../decisions/0172-where-a-set-aside-session-stands-is-its-note.md)): the note stays, through Clear set aside, a prompt there and the day coming, to be read when the session is picked up.
The note is written only when the line changed, a blank one removing it as in Edit note…, which stays in the menu.
A choice is written as text and read by one grammar for main's check of the setting and the window's dialog (`shared/status/set-aside.ts`): `whenever`, `in <N>m` or `in <N>h` from the press, `in <N>d` or `in <N>w`, `tomorrow`, or `next <weekday>`, the first such day after today, so on a Monday `next monday` is a week on; a day may end in a time of day.
Its words are English whatever the language setting, as the app's other words are.
The choices are offered in the order their moments come, worked out when the dialog opens, two at the same moment once, then Pick a date…, then Whenever, so a day is what comes to hand first ([decided 2026-11-04](../decisions/0160-set-aside-choices-come-in-the-order-of-their-moments.md)).
A choice in minutes or hours is named by its moment as the dialog opened and set from the moment Set aside is pressed.
A list with a choice the app cannot read is not used at all, the default list in force and the choice named under the field, as every setting's value is either used or not ([decided 2026-11-05](../decisions/0168-a-set-aside-list-with-a-bad-choice-is-not-used.md)).
The dialog names the session in its title, "Set aside: <title>", as the Note dialog does ([decided 2026-10-29](../decisions/0146-the-set-aside-dialog-names-the-session.md)); from the bar of selecting several it names how many ([§ Selecting several](session-list.md#selecting-several)).
A choice with a day and no time of its own comes due at the time of day the settings give (`setAsideTime`, `"09:00"` by default), in local time, so a week on across a change of the clocks is still that time, though a time the change skips that day comes due as much later as the change; Pick a date…'s time starts at it ([decided 2026-10-29](../decisions/0139-a-set-aside-day-comes-due-at-a-set-time.md)).
A prompt of yours there takes it off, by the needs-you mark's test (`startedByClaude`), and so do Clear set aside, a finish, whose Undo gives it back as it was, and a delete; opening the session does not, so a look leaves a dated reminder in place.
It shows as a bookmark, chosen from a mock over a calendar, an hourglass, a come-back arrow and a snooze "z": a pill on the session row beside the clock, and the bare icon on the tab, as the clock is (`set-aside-mark.ts`, through `icon-mark.ts`, which builds both); its tooltip and a line of the menu's header say "Set aside, whenever" or "Set aside until Tue 3 Nov, 09:00", with the date, since a weekday alone is unclear past a week; it does not repeat the note, which the note mark beside it shows on hover and the menu's header by its first line.
The list's set-aside filter pill, the bookmark its icon, shows every session so marked, with a tab or without (`setAsideOnly`), in the place of the paused pill it replaced; an older stored view's paused pill reads as off.
**Its moment coming makes the session need you**: the window looks at launch, once the store has both marks, then when the soonest mark is due and whenever the marks change, waiting an hour at the most between looks (`settleDueSetAside`, `lookForDue`), so a moment that passed while the app was closed shows from the first draw and one that comes while it runs shows then; the mark goes, a session not marked as needing you is marked with the reason `reminder`, "Needs you — reminder for Tue 3 Nov, 09:00", from the moment it was for, and one already marked keeps its mark, its reasons and their times.
The window rather than main, since the window holds both marks and is the only reader, so nothing has to be pushed to it.
**The two marks are kept apart, and the order they came in decides what shows**, by when each was set (`mutedBySetAside`), so it holds over a restart where a read mark does not ([decided 2026-10-29](../decisions/0143-set-aside-and-needs-you-marks-are-kept-apart.md)).
A needs-you mark whose every reason is from before the set-aside mark is muted while the set-aside mark stands (`mutedNeedsYou`): where its dot shows the mark, it is dimmed, as read, with its reason in the tooltip, and the roll-ups follow the dot (`sessionPart`), so it counts for nothing in them; claude's status, working, asking or at its prompt, shows over the mark whatever the order says and counts as it does for any session (`mutedGivesWay`, [decided 2026-11-11](../decisions/0210-a-muted-needs-you-mark-gives-way-to-claudes-status.md)).
When its moment comes the mark keeps that reason rather than taking the reminder's, and shows in full again.
One that came after it is news the set-aside mark did not know of, so it shows and counts in full, the bookmark beside it; unless `setAsideNews` is `"wait"`, which mutes every reason while the set-aside mark stands, news included, until its day, or with whenever until the mark goes (`mutedBySetAside`, [decided 2026-11-12](../decisions/0215-news-while-set-aside-can-wait-for-its-day.md)).
Undo of a close or a finish puts a needs-you mark back with the tab, from when it was marked, so one a set-aside mark muted is muted again.

**A task claude has scheduled shows as a clock beside the session.**
`Stop` lists what is scheduled for the session, a `/loop` wakeup or a cron not made durable (a durable one goes to a file of claude's instead), as `session_crons`, each entry its prompt, its schedule and whether it repeats, and the script keeps the whole payload as `<id>.stop`, which main reads on every change and hands the window on a channel of its own (`session:scheduled`): a fact about the session rather than a state, like a model switch, since a task waits through every status until it fires, and the busy of the next turn must not take it away.
The list cannot tell a cron from a `/loop` wakeup, and a stop does not end them alike, as the section on stopping a session says, so main looks each listed task's id up in the session's transcript (`cronSchedules`): a `CronCreate` call's result names the cron's id with its schedule in claude's words, `{"id": "34f607db", "humanSchedule": "Every 10 minutes", …}`, and a `ScheduleWakeup` call's names no id at all, so a task found there is a cron and any other a wakeup (`ScheduledTask.cron`).
Seen in session f3829708 on 2026-10-24, whose list named a cron by the id its transcript gave it and a wakeup by one it gave nowhere.
A subagent's calls are kept in a transcript of their own (seen in session 2e8cf79b), so a cron a subagent made would read as a wakeup; not tried.
Main reads a transcript on from where its last look stopped, since one only grows and can run to tens of megabytes, and only for a list that names a task.
The window keeps the tasks (`scheduledTasks`), and one mark draws them, on the session's tab and its row (`scheduled-mark.ts`), the tooltip naming each task, a cron's schedule, and what a stop does to it (`afterStop`): "say hi · Every 10 minutes · comes back when you open the session", or "/loop say tick · ends with the session".
The clock in its own colour goes when a later turn ends with nothing scheduled, when the app drops the session's status files (its tab closed or gone cold, where a muted one may take its place, below), and from a session a tab's claude left by `/clear` or its own `/resume`, which no claude of the app's runs any more though nothing says its list emptied.
An end the app reports in a hook's place (below) is written over `<id>.stop` too, so it carries the last `Stop`'s list on, with its transcript's path, or every interrupt would take a cron's clock away while the cron still waits.
The list is the last `Stop`'s, so it can be behind: by claude's source an interrupt, and an Esc at its prompt, cancel a pending `/loop` wakeup without a `Stop`, and the clock stays until the next one.
It is not read at launch: no claude outlives a quit.
A start other than a compaction's writes `<id>.stop` as `{}`, which main takes as no news rather than as nothing scheduled, and sends nothing for (`readScheduled`), as it does for a `Stop` without the list; an end the app reports in a hook's place before any `Stop` carries no list either, rather than an empty one.
A resumed claude brings its crons back (measured on claude 2.1.302, below), and those show only from its next `Stop`: its `SessionStart` carries no list of them (measured with `--resume`, and so by claude's source), and a `/loop` wakeup did not come back in either run measured, though claude's source has a path that re-arms one still pending, so nothing before that `Stop` can say which came back.

**A tab whose claude has gone keeps its clock, muted, for the crons that come back.**
The tab keeps the crons its session had when its claude went (`TabState.scheduledWhenStopped`), which come back when the session is opened again, and its clock goes on showing them, muted as a worktree mark can be, on its tab and its row, under "Scheduled when stopped:" (`clockOf`, `scheduled-mark.ts`; [decided 2026-10-24](../decisions/0109-a-stopped-tab-keeps-a-muted-clock-for-its-crons.md)).
A `/loop` wakeup ends with the session, so it is not kept, and a session that had only wakeups keeps no clock.
It stays through a start of its claude until that claude reports (`scheduledReported`): the report's list then shows in the clock's own colour, or the clock goes for none; a claude stopped again before it reported leaves what the tab kept, which is still all that is known.
A tab started again before the app has dropped its last claude's status files loses it early: their going reads as a report of nothing scheduled.
It is the session's, so a claude that moves the tab on to another session by `/clear` or its own `/resume` takes the tab without it.
It is kept for the next launch beside the open tabs (`scheduledWhenStopped` in meta, written in a call of its own after `setOpenSessions`, for the open sessions only).
A quit forces every claude out, after which a cron came back and a `/loop` wakeup did not (measured, as for a stop), and the exits it causes write nothing, since the open tabs are not written once the app is quitting; so as the window hears of the quit, which main tells it before it ends any claude, each tab still running keeps what its stop would have kept, and that is written then (`whenQuitting`).
A session running at a quit comes back (marked as needing you, by default) with a muted clock if it had crons.
Main does not wait for that write, and nothing holds the quit for it: it normally lands while the quit waits for the sessions it ended to go, which, with a session running, is at least one 50 ms look (`untilGone`) and usually longer.
The cost of no news: a claude too old to list its tasks in `Stop` would keep a restarted tab's muted clock until it goes (claude 2.1.302 lists them).
The session's menu says it too, in the clock's own words ([§ A session's menu holds everything about it](claude.md#a-sessions-menu-holds-everything-about-it)).

**A subagent's events arrive as the session's, and once its turn has ended they are not the session working.**
Hooks fired inside a subagent carry the session's own id, told apart by `agent_id`, so a background subagent's tool call wrote busy over a session that was ready, and the dot went ready, busy and ready again with nobody doing anything.
The script never writes busy for such an event over ready or background.
Waiting still goes through, since a question must never be held back, and a foreground subagent is unaffected, since its session is busy or waiting for as long as it runs.

**An interrupt, work stopped from claude's task list, and a prompt turned down with feedback fire no hook, so the transcript ends them.**
Ctrl+C or Esc interrupting a turn during a tool or while claude writes fired nothing, nor did Esc at a permission prompt (measured once), nor a shell or a monitor stopped from `/tasks` (all on claude 2.1.289), so the dot stayed busy, waiting or background until claude's next turn.
Both are written to the transcript: an interrupt as a user record saying exactly `[Request interrupted by user]` or `[Request interrupted by user for tool use]`, and the end of a piece of work as a queued `<task-notification>` naming its id and how it ended, `killed`, `completed` or `failed`.
**The transcript may end a state the hooks started, and never start one from nothing**; everything else is the hooks' alone.
So the main process reads each transcript whose session has a status, all of it the first time and then only what was added, and ends the turn as a `Stop` would when an interrupt was written after a busy or a waiting, and ends background once all the work its `Stop` listed has an end.
It also ends a waiting with busy when a refusal of the tool call (its result begins "The user doesn't want to proceed with this tool use.") was written after it and no interrupt follows: that is a prompt turned down with feedback, the question answered and the turn going on; turned down without feedback, the interrupt follows within milliseconds (measured) and ends the turn instead.
To know what still runs after an interrupt, the script keeps each `Stop`'s payload beside the status, as `<id>.stop`, since the next turn's busy overwrites the status itself; a fresh start keeps `{}`, and a compaction keeps what was there.
Work that `Stop` listed, and a shell, a monitor or a subagent the interrupted turn sent off in the background (each one's tool result carries the id `Stop` would list it under), still run unless an end was written for them after that `Stop`: background work survives an interrupt, and its end starts a turn of its own (measured with shells, and taken to hold for the other two), so the session reads background until then.
An end written before the `Stop` does not count, since claude can reuse an id, as for a subagent resumed after it finished; a list the app reports itself keeps the time of the `Stop` it was taken from, so work stopped while the app was reporting it still counts as ended.
Any other kind of work started in the interrupted turn itself is not counted, since none was measured, and the session reads ready until that work's own turn; a monitor is known by its whole result, since other tools' results, a workflow's among them, carry a task id too, and one on a websocket, whose result is the same, is counted as a shell where its `Stop` would say monitor.
A finished shell and a subagent stopped from `/tasks` each started a turn of their own, its `UserPromptSubmit` 85 to 136 ms after the notice (three measured), so every end, an interrupt's too, waits a second for a hook to answer it, and is reported only if none has written the status meanwhile; the transcript is read again after the wait, so what claude wrote meanwhile, such as the interrupt after a refusal, counts.
The end goes through the hook script, run as the hook would have been, for a ready as for a `Stop` with the work still listed, so the script stays the one writer of the status files and the end reads exactly as the hook's would; the file names `transcript:interrupt`, `transcript:task-end` or `transcript:refusal` as the event.
Each end also names the statuses it ends and the second the status it read was stamped with, and the script, as the last thing before its write and with builtins only, writes nothing over any other: a hook that wrote meanwhile, a `Stop` above all, keeps its word, unless it lands in the few microseconds between that look and the write.
A waiting written after the interrupt is taken as a question claude asked since, and stands; whether claude still sends a prompt's notice, about six seconds late, after Esc has dismissed the prompt is not measured, and such a notice would leave waiting until the next hook.
A hook that rewrites the same status within the same second, such as a prompt's busy over busy just after an interrupt, is still overwritten, until its next tool call or its `Stop`.
Claude's idle notice did not follow an interrupt during a tool or while it wrote in the 80 seconds watched after each of three (measured on claude 2.1.289), so the ready such an interrupt leaves stays ready; after Esc at a permission prompt only 11 seconds were watched.

Two more events are not that simple, and both cost a wrong guess to work out.

**Compaction is work, so it reads as work.**
`PreCompact` → busy, and the END of a compaction is a `SessionStart` carrying `source=compact`, which the script rewrites to ready.
`PostCompact` looks like the obvious end signal and is not used: a probe never observed it firing and could not prove it ever does, while `SessionStart` was observed.
That follows from what the states mean here — **ready is "claude has stopped, and your input is required to continue", not merely "not busy"** — so a session thinking about its own transcript is busy, and green when it comes back.

**A model switch is neither, so it gets its own file.**
A transcript records which model *answered*, never which one was chosen, so `/model` leaves no trace in it until the next reply — and the row went on naming the old model in between.
`PostModelSwitch` is the only place that answer exists at the moment it becomes true; its payload carries `from_model`, `to_model` and `source`, and `to_model` is written to `<id>.model` beside the status rather than into it, because the two answer different questions about the same session.
The renderer prefers it over the transcript's and keeps it **in memory only**: every switch in a session this app runs lands there, so it can never be staler than the file, and after a restart the transcript's own last answer is the right source again.

**`SessionStart` is mostly identity, not state.**
Its session id is what the terminal is running *now*, which is the only way to follow a `/clear` or claude's own `/resume` ([§ A resumed session is the session it was](claude.md#a-resumed-session-is-the-session-it-was)).
For every source but `compact` the script writes the terminal's token and the source to `<id>.start`, a file of its own as a model switch's is, which main passes on and the renderer applies to the tab.
It also writes an identity-only marker into the status file, never shown as a dot, and refuses to overwrite an existing status file there — these files seed the dots at launch, and the event also fires mid-session, where a real status is worth keeping.
That refusal is why the start has a file of its own: `/resume` goes on in a session that has a status already, and the tab would otherwise hear of it only with the session's next status, such as its next prompt.
For the same reason that marker is dropped when the launch state is read back: identity is answered by the tabs being restored around it, and seeding it would hand the renderer a status no dot has wording for.

**`SessionEnd` ends the session it names, every time — including `clear` and `resume`.**
Those two leave the *process* running, which makes them look like exceptions, and one was written here on that basis and reverted the same day.
This app tracks **sessions, not processes**: `/clear` writes a last line to the old transcript and opens a new file under a new id, so the id the event carries really is finished, and declining to close it leaves a dead session showing a live dot for good.
The process's next session arrives separately, as the `SessionStart` above.

The general shape, for any hook added later: **ask what the event means for a SESSION before mapping it to a state.**
An event named for a lifecycle is not necessarily about the lifecycle you are tracking.

The cleanup of hooks an older version injected into `~/.claude/settings.json` scans every event in that file rather than the ones this version registers, so an entry for an event since dropped is still found.
A hook also has about a second to answer before Claude Code moves on, so it must never wait on anything: answer, then finish detached.
The script is covered by tests that run it the way Claude Code does — argument, JSON on stdin, `CLAUDE_UI` set — because it is the one part of the app that executes outside it.

The hooks are scoped to claude-ui: it sets `CLAUDE_UI=1` on the terminals it spawns, and the hook script no-ops unless that variable is set, so sessions run in a plain terminal are left untouched.
When it does fire, the script writes `~/.config/claude-ui/status/<id>.json`.
The main process watches that directory and pushes updates to the renderer, which shows a dot per session: busy, ready, working in the background, waiting, or hollow (`closed` and unknown states have no color).

A session's status is forgotten, its file removed, when its tab is closed, when its tab goes cold because its claude has gone, and when a launch marks it as needing you.
The second is for a claude that never reports its end: a `SIGKILL`ed one cannot run its `SessionEnd` hook, and its last busy or waiting went on nudging from the session's dot and from the roll-ups over it, such as its project's in the switcher.
A `SessionEnd` that does arrive writes `closed`, which draws the same hollow dot as no status at all.
